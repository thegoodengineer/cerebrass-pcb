# ClawBoard

An autonomous PCB design-review agent. It reads a KiCad project, runs real DFM and ERC
checks, repairs the schematic and board in place, and shows the board changing live while it
works. The agent harness is **OpenClaw**; the model is **Moonshot Kimi K3.1 Pro on Cerebras**
(`moonshotai-kimi-k3.1-pro-trial`).

```
 ┌──────────────┐   chat.completions    ┌─────────────────────────────┐
 │   OpenClaw   │ ───────────────────▶  │ Cerebras  api.cerebras.ai/v1 │
 │ agent harness│ ◀─── tool calls ───   │ moonshotai-kimi-k3.1-pro-trial│
 └──────┬───────┘                       └─────────────────────────────┘
        │ MCP (stdio)
 ┌──────▼──────────────────────────────────────────────┐      ┌───────────────────────┐
 │ pcb-tools  (Python, standard library only)          │      │ web  (Vite + React)   │
 │  inspect_kicad_project   run_dfm_and_erc_audit      │ SVG  │  live board viewer    │
 │  apply_pcb_patch         render_board_svg           │ ───▶ │  agent trace, TPS,    │
 │  S-expr parser · router · rule engine · renderer    │      │  benchmark lanes      │
 └──────┬──────────────────────────────────────────────┘      └───────────────────────┘
        │ reads / writes
   *.kicad_sch  *.kicad_pcb   (open natively in KiCad 8 / 9 / 10)
```

## Quick start

```bash
./setup.sh                 # Windows PowerShell: ./setup.ps1
# put CEREBRAS_API_KEY (and BASELINE_* for the benchmark) in .env
npm run dev                # http://localhost:3000
```

No key yet? Tick **Simulated** in the top bar. It runs the complete loop (real tools, real
board edits) against a scripted model with synthetic timing, and watermarks everything
`SIMULATED`. It is for rehearsal only and is never a benchmark result.

Requirements: Python 3.10+, Node 18+ for the dashboard. OpenClaw itself needs Node 24.16+.
KiCad is optional (it enables the independent DRC/ERC check).

## What is in the box

| Path | What |
|---|---|
| `pcb-tools/` | The tool server: `mcp_server.py` (MCP over stdio), `cli.py`, the `clawboard` package, fab and datasheet rules, tests |
| `sample_board/` | ESP32-S3 USB-C sensor + motor controller with six planted bugs (generated by `pcb-tools/make_sample_board.py`) |
| `web/` | Dashboard on `localhost:3000`, plus the run controller, metering proxy and simulated endpoint |
| `openclaw_config/` | `openclaw.json`, the agent workspace (`AGENTS.md` = the static system prompt) and the `clawboard-pcb` skill |
| `setup.sh` / `setup.ps1` | Environment check, install, self-test, OpenClaw config resolution |
| `DEMO_SCRIPT.md` | 45-second shot list for the recording |

## The four tools

| Tool | Returns |
|---|---|
| `inspect_kicad_project(project_dir)` | Components, nets with pin names, track widths, vias, drills, zones, tightest clearance, unrouted airwires. About 1.5k tokens for the sample; never raw S-expressions. |
| `run_dfm_and_erc_audit(project_dir, fab_house="jlcpcb")` | `pass`, counts, and `issues[]` with `id`, `rule`, `severity`, `title`, `detail`, `refs`, `nets`, `at`, `fix`. |
| `apply_pcb_patch(project_dir, operations)` | Per-operation result, the error count after each step, and a final audit summary. |
| `render_board_svg(project_dir)` | Writes `web/public/board_preview.svg` and `schematic_preview.svg`. Runs automatically after every audit and patch. |

**Rules checked:** USB-C CC pull-downs, decoupling per IC supply pin (value and distance, from
`rules/parts.json`), I2C pull-ups, floating pins, schematic/PCB sync, fab minimum track width,
power track width (IPC-2221), copper clearance and shorts, unrouted nets, ground-pour islands,
via geometry, copper-to-edge, placement grid, courtyard overlap.

**Patch operations:** `set_pin_net`, `add_component`, `move_footprint`, `set_track_width`,
`route_net`, `reroute_net`, `ripup_net`, `move_via`, `delete_via`, `add_via`, `add_track`,
`stitch_pour`, `rename_net`, `set_value`.

The agent states intent ("100 nF from +3V3 to GND near U1.2"). The tool solves the geometry:
it finds the nearest free grid spot whose pads clear every other net, and routes with an A*
maze router (0.25 mm grid, Manhattan and 45 degree moves, both copper layers, vias when
needed). Every new primitive is re-checked with exact geometry before it is committed.

Try them by hand:

```bash
python pcb-tools/cli.py audit sample_board --pretty
python pcb-tools/cli.py patch sample_board --ops '[{"op":"route_net","net":"UART_TX"}]' --pretty
python pcb-tools/cli.py oracle sample_board --pretty     # KiCad's own DRC/ERC
python pcb-tools/make_sample_board.py                    # regenerate the broken board
```

## The sample board and its six bugs

ESP32-S3-WROOM-1, USB-C input, AMS1117-3.3, BME280 on I2C, DRV8833 motor driver. 64 x 44 mm,
2 layers, ground pours on both sides, 25 footprints.

| # | Bug | Audit id |
|---|---|---|
| 1 | USB-C CC1 and CC2 tied together on one 5.1k resistor | `USB-CC-J1` |
| 2 | No 100 nF decoupling capacitor at the ESP32 3V3 pin | `DECAP-U1-100nF` |
| 3 | No pull-ups on I2C SDA / SCL | `I2C-PU-I2C_SDA`, `I2C-PU-I2C_SCL` |
| 4 | `+5V_VBUS` routed at 0.1 mm instead of 0.5 mm | `PWR-W-+5V_VBUS` |
| 5 | GND via 0.05 mm from a signal track | `CLR-GND-UART_RX` |
| 6 | `UART_TX` unrouted; the BME280 decoupler 19 mm away and off-grid | `UNROUTED-UART_TX`, `DECAP-FAR-C5`, `PLACE-GRID-C5` |

The project ships its own symbol and footprint library plus a `.kicad_dru`, so opening it in
KiCad and running DRC shows the same faults.

## Dashboard

- **Left:** live PCB and schematic viewer. Patched copper glows green/cyan and draws itself
  in; open DFM errors pulse red. Scroll to zoom, drag to pan, hover a net to trace it, switch
  F.Cu / B.Cu / both.
- **Right:** agent execution trace (each model call with tokens, tokens/sec and first-token
  time; each tool call; each patch operation with the errors left after it), the measured
  error-count chart, and the verification ladder.
- **Top bar:** `Run audit & fix`, and `Cerebras vs. Standard GPU`, which runs the identical
  task on both endpoints side by side.

### How the benchmark is measured

- Both lanes get the same system prompt, tools, task and a fresh copy of the same board.
- **Tokens/sec** = completion tokens / time from first streamed token to end of response,
  summed over all calls. Token counts come from the API `usage` field; if an endpoint sends
  none, they are estimated from characters and the report says so.
- **LLM time**, **tool time** and **harness setup** are shown separately. Tool time is the same
  work on both lanes, so the headline ratio is LLM time.
- **Total elapsed** runs from a lane's first model request to its sign-off (model time plus tool
  time). Harness setup and Gateway warm-up are excluded because they depend on start order, not
  on the model.
- The comparison shows correctness next to speed: operations applied, audit result and the
  KiCad oracle for each lane. A fast run that leaves errors does not count as a win.
- Every run writes a per-request report (timestamps, first-token time, usage, both TPS
  definitions, audit before/after, step log, oracle). The `report.json` link on each lane opens it.

Working copies and reports live in the OS temp directory (`clawboard-runs/`) because the tools
rewrite them many times a second; set `CLAWBOARD_RUNS_DIR` to change that.

## OpenClaw wiring

`openclaw_config/openclaw.json` (validated with `openclaw config validate`, OpenClaw 2026.11.6):

- provider `cerebras` -> `https://api.cerebras.ai/v1`, `api: "openai-completions"`,
  `apiKey: "${CEREBRAS_API_KEY}"`, model `moonshotai-kimi-k3.1-pro-trial`
- agent `clawboard` under `agents.entries`, workspace `openclaw_config/workspace`
- MCP server `clawboard-pcb` -> `python pcb-tools/mcp_server.py`
- `tools`: `toolSearch: false`, `codeMode: false`, `allow: ["clawboard-pcb__*"]`
- skill directory `openclaw_config/skills`

The `tools` block matters. By default OpenClaw hides MCP tools behind `tool_search` /
`tool_describe`, and with that switched off it sends all of its roughly 50 built-in tools
(about 36k tokens per request). Allowing only `clawboard-pcb__*` puts exactly the four PCB tools
in the model's tool list, keeps each request near 10k tokens, and means the agent cannot run
shell commands or edit files on your machine. Widen `tools.allow` if you want the skill's
command-line fallback.

`setup` writes `openclaw.resolved.json` with absolute paths. One-shot use from a terminal:

```bash
export OPENCLAW_CONFIG_PATH="$PWD/openclaw_config/openclaw.resolved.json"
export CEREBRAS_API_KEY=...
openclaw config validate
openclaw mcp doctor clawboard-pcb --probe
openclaw agent exec --config "$OPENCLAW_CONFIG_PATH" --cwd "$PWD/openclaw_config/workspace" --json \
  "Audit and repair the KiCad project in project_dir: $PWD/sample_board"
```

### How the dashboard drives OpenClaw

`openclaw agent exec` re-loads OpenClaw's plugin registry on every call (60-100 s on the
development laptop), which is no use for a live demo. So the dashboard keeps one **OpenClaw
Gateway** warm and starts each agent turn with a single HTTP request to the Gateway's
OpenAI-compatible endpoint:

1. On start-up the dashboard launches `openclaw gateway` on `127.0.0.1:18931` with a generated
   runtime config (its own state directory under the temp folder, a random token, one agent per
   benchmark lane, `gateway.http.endpoints.chatCompletions.enabled: true`). The status strip
   shows `OpenClaw gateway: warming up` and then `ready`; the first start takes one to three minutes.
2. Each lane's run is `POST /v1/chat/completions` with `model: "openclaw/clawboard-<lane>"`.
   OpenClaw runs the whole agent turn (prompt assembly, model calls, MCP tool calls) and returns
   the sign-off.
3. In the runtime config each lane's provider points at a local pass-through
   (`/llm/<lane>/v1`) that forwards every request to the real endpoint unchanged and meters the
   stream. That is where the live tokens/sec, first-token time and token counts come from.
4. The Gateway prepares sessions one at a time, so in a comparison the second lane's turn is
   released when the first lane has sent its first model request. Each lane's **Total elapsed**
   runs from its own first model request to sign-off; **Harness setup** is shown separately.

`Engine: auto` uses OpenClaw when the CLI and Node 24.16+ are present, and otherwise a built-in
OpenAI-compatible loop with the same prompt and the same MCP server. The Gateway uses about
1.4 GB of memory while it runs; set `CLAWBOARD_NO_PREWARM=1` to start it only on first use.

### Prompt caching and the 100K TPM limit

`openclaw_config/workspace/AGENTS.md` holds everything static: workflow, operation reference,
KiCad file facts, JLCPCB 2-layer and 4-layer limits, IPC-2221 table, and datasheet rules for
ESP32-S3, STM32, USB-C, BME280, DRV8833 and AMS1117. It has no timestamps or per-run content,
so every request in a loop shares the same prefix. OpenClaw injects it into its system prompt
and puts the date and other per-run context in a later user message, so the prefix stays
cacheable. The tool schemas are static too.

Measured with the simulated endpoint (token counts are its character-based estimate, so treat
them as approximate): one full run through OpenClaw is 4 model calls, about 39k prompt tokens
in total with about 59 % of them a repeat of the previous call's prefix, and about 600
completion tokens. The built-in loop sends about 22k. On Cerebras, cached tokens count toward
the total-TPM bucket but not the uncached one, so two runs per minute fit under 100K. A
comparison run uses the Cerebras budget once; the baseline lane has its own.

## Verification

Three rungs, reported separately and never substituted for one another:

1. **Patch post-conditions.** Every track, via and pad the patch tool adds is checked against
   all other copper with exact geometry before it is written. Files are replaced only after a
   structural integrity check, and the original is kept in `.clawboard/original/`.
2. **ClawBoard audit.** The full rule set, re-run after every operation (the measured step log).
3. **KiCad oracle.** `kicad-cli pcb drc` and `sch erc` on a copy of the project. A different
   implementation, so it cannot share our bugs. It takes 15-40 s, so it runs once after the
   agent signs off and is not part of the timed loop.

Measured on this machine (KiCad 10.0.4, `python pcb-tools/cli.py oracle`):

| Board | ClawBoard audit | KiCad DRC | KiCad unconnected | KiCad ERC |
|---|---|---|---|---|
| `sample_board` as shipped | 8 errors, 1 warning | 29 errors (1 clearance, 28 track width) | 1 (`UART_TX`) | 0 errors |
| after the nine-operation fix | 0 errors, 0 warnings | 0 errors | 0 | 0 errors |

KiCad also reports about 80 silkscreen warnings (reference text over pads) on both; they are
cosmetic and unrelated to the planted bugs.

```bash
npm test        # 9 tests: parser round-trip, netlist sync, the six bugs, the fix, MCP protocol
```

## Design principles

| Principle | Where it is here |
|---|---|
| Verify in separate stages and never report one stage's result as another's | The three rungs above; the agent prompt forbids claiming the KiCad result |
| Every number is backed by a record | Per-request `report.json` behind every lane; simulated runs are labelled in the UI and in the report |
| Report correctness next to speed | The benchmark shows audit and oracle status per lane, not only tokens/sec |
| Measure every step | Error count before and after every patch operation, drawn as the step chart |
| Keep the inner loop fast; run expensive checks once at the end | Audit inside the patch call (no extra model round trip); KiCad DRC once after sign-off |
| Reject bad data instead of using it | Integrity-checked writes, rejected operations with reasons, pristine backup |
| People define what correct means; the agent explores | The static contract in `AGENTS.md`; audit `fix` hints are suggestions, not orders |
| Cut per-call overhead | One persistent MCP tool process per run instead of a new interpreter per call |

## What has and has not been verified

Verified on the development machine (Windows 11, Python 3.12, Node 24.22.3, OpenClaw 2026.11.6, KiCad 10.0.4):

- the test suite, the sample generator, and the full fix cycle
- KiCad's DRC/ERC opening both files and agreeing with the audit, before and after
- `openclaw config validate`, `openclaw mcp doctor clawboard-pcb --probe`, and a complete
  `openclaw agent exec` run
- **live**: Kimi K3.1 Pro (`moonshotai-kimi-k3.1-pro-trial`) on Cerebras driving the agent through
  the OpenClaw Gateway. One patch of 9 operations took the board from 8 errors to 0, KiCad
  reported 0 DRC errors, 0 unconnected items and 0 ERC errors, and the run measured 591
  tokens/sec with 68 % of prompt tokens served from the prompt cache (4 model calls, 14.2 s
  from first model request to sign-off, during a period when the trial endpoint was returning
  "high traffic" 429s that the dashboard retried)
- the same live model through the built-in loop
- both benchmark lanes through OpenClaw and through the built-in loop, using the Simulated endpoint

Still not verified:

- a baseline endpoint for the comparison lane (none was configured), so no live
  Cerebras-versus-GPU ratio has been measured
- the model's context window in `openclaw.json` (131072) is a placeholder: set the real value.

## Limits

- Footprints are simplified land patterns generated by `clawboard/library.py`. Check them
  against vendor drawings before fabricating anything.
- The schematic reader handles a single flat sheet (wires, junctions, labels, power symbols);
  hierarchical sheets and buses are not supported.
- The board outline is treated as its bounding rectangle. Arcs, zones with cut-outs and
  blind/buried vias are not modelled.
- The pour model is a conservative 0.25 mm-grid approximation of KiCad's zone fill. Zones are
  written unfilled: press `B` in KiCad to fill them.
- JLCPCB numbers in `rules/jlcpcb.json` were read from their capabilities page on 2026-11-22.
  Confirm them before ordering.
- Tool time (about 4 s for the nine-operation patch) is pure-Python geometry. It is the same
  on every lane, but it does bound the end-to-end speed-up.
